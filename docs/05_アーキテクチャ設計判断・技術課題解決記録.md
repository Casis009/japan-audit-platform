## ADR-01 監査ログはサーブレットフィルターで取る

- **背景**：業務アプリごとにログ出力を足すと、改修と回帰テストの工数が大きい。
- **決定**：業務の前段にフィルターを1つ挟み、業務処理は監査を一切知らない構成にする。
- **理由**：業務コードの変更がゼロで済む。全リクエストを漏れなく通せる。
- **捨てた案**：AOP（業務メソッドへの横断処理）…業務の作りに依存する。DB のトリガー…「誰が見たか（参照）」が取れない。
- **トレードオフ**：HTTP 以外（バッチ・DB 直接操作）は取れない。要件定義でスコープ外とした。

## ADR-02 本文は「読んだ分を素通しし、先頭だけコピー」する

- **背景**：監査には本文の中身が必要だが、本文は1回しか読めない。
- **決定**：業務側が読んだバイトをそのまま流しつつ、先頭の上限（既定64KB）だけを監査用にコピーする（Read-Through / Tee）。
- **理由**：業務側に届くデータを1バイトも変えない（非侵襲の保証）。メモリ使用量に上限がある。
- **捨てた案**：先に全部読んでから渡す…巨大なアップロードでメモリを使い切る。旧実装は上限で切ったものを業務側に渡しており、200KB の送信で業務に64KBしか届かなかった（第7章）。
- **トレードオフ**：上限を超えた部分の個人情報は数えられない。業務側が本文を読まなければコピーも空になる。

## ADR-03 マスキングはセンサー（業務サーバー内）で行い、生値をプロセス外へ出さない

- **背景**：監査ログ自体が個人情報の塊になると、監査基盤が新たな漏えい源になる。
- **決定**：検知・マスキングはフィルター内で行い、送信・退避・DB にはマスキング値と件数だけを流す。本文は既定で送らない。
- **理由**：ネットワーク・ディスク・DB のどこにも生値が残らない。氏名・住所は形式で検知できないため、本文を送らないことで補う（データ最小化）。
- **トレードオフ**：検知のための CPU 時間は業務サーバー側で使う（本文は上限付きなので数ms以内。検証手順書に実測値）。

## ADR-04 マイナンバーは「チェックディジット＋文脈」で判定する

- **背景**：12桁の数字は注文番号・口座番号などにも多い。
- **決定**：モジュラス11（番号法施行令第8条）で検証し、さらに直前のキーワードで確度 HIGH / MEDIUM を付ける。マスキングは MEDIUM も含めて行う。
- **理由**：正規表現だけより誤検知を大きく減らせる。ただしランダムな12桁でも約10%は検証を通る（単体テストで実測）ため、「誤検知ゼロ」とは言えない。
- **トレードオフ**：過剰にマスキングすることがある。監査の目的上、見逃し（漏れ）より過検知のほうが安全と判断した。

## ADR-05 送信は非同期・失敗時はローカル退避（フェイルオープン）

- **背景**：監査基盤の障害で業務が止まってはいけない。一方、監査ログを失ってもいけない。
- **決定**：上限付きキュー → 送信スレッド（仮想スレッド）。失敗時・満杯時はローカルファイルへ退避し、再送スレッドが復旧後に送り直す。失敗後の一定時間は送信を試みない（サーキットブレーカー）。
- **理由**：業務スレッドは `offer()` するだけで待たない。止まっているコレクターに毎回タイムアウトまで待つとキューが詰まるため、ブレーカーで即退避する。
- **捨てた案**：失敗時に業務を止める（フェイルクローズ）…業務への影響が大きい。メモリに溜め続ける…OOM でサーバーが落ちる。
- **トレードオフ**：退避ファイルにも上限がある。超えたら破棄して件数を数える（ディスク溢れで業務サーバーを止めないことを優先）。破棄件数は監視対象とする。

## ADR-06 再送は「受信側で冪等」にして安全にする

- **背景**：再送の途中で失敗すると、どこまで届いたか分からない。
- **決定**：コレクターは traceId で重複を判定し、2回目は 200（DUPLICATE）を返して何もしない。センサーは途中で失敗したら未送信分だけを残す。
- **理由**：「少なくとも1回届ける」方式で、二重に届いても結果が同じになる。
- **補足**：恒久的に拒否された電文（400・413）は rejected.jsonl に移す。これがないと不正な1件が後ろの正常なログの再送を止めてしまう。

## ADR-07 DB に書けなければ 503 を返す

- **背景**：旧実装は DB 保存に失敗しても 202 を返していた。
- **決定**：保存できなかったら 503。
- **理由**：2xx を返すとセンサーは「届いた」と判断して退避しないため、ログが消える。失敗は送信元へ正しく伝える。

## ADR-08 ハッシュチェーンは「受信順」に「直列化して」連結する

- **背景**：監査ログは後から書き換えられないことを示す必要がある。内部の DB 管理者も脅威になる。
- **決定**：
  1. チェーンの先頭を1行のテーブルに置き、挿入トリガーで `FOR UPDATE` ロックしてから採番・連結する。
  2. 順序は業務の時刻ではなく受信順の連番（chain_seq）にする。
  3. UPDATE / DELETE / TRUNCATE はトリガーで拒否する。
  4. 検証関数で、内容の書き換え・欠番・末尾削除を検出する。
  5. 一定間隔で先頭のハッシュを DB の外（アンカーファイル）に書き出し、照合する。
- **理由**：
  - ロックなしだと同時挿入で同じ直前行を参照し、チェーンが分岐する（旧実装で40件同時に8か所）。
  - 再送で古い時刻のログが後から届くため、時刻順では連結が崩れる。
  - DB 管理者はトリガーを外して全行を再計算できる。DB の中だけの検証では見抜けないので、外部のアンカーと照合する（実際に再計算攻撃を行い、DB 内検証は「正常」、アンカー照合で「改ざん」と出ることを確認した）。
- **トレードオフ**：挿入が1本に直列化されるため、書き込み性能に上限がある。大規模では「チャンク単位でまとめてハッシュする」「Merkle Tree」等に変える。アンカーファイルも本番では別サーバー・WORM ストレージ・タイムスタンプ局に送るべき。

## ADR-09 警戒閾値は「本人数100人超」・時間窓の累計でも判定

- **背景**：大量照会は内部不正の典型的な兆候。
- **決定**：異なるマイナンバーの数（≒本人数）が100人を**超え**たら CRITICAL。同一ユーザーの10分累計でも判定する。
- **理由**：番号法の報告基準（委員会規則第2条：本人の数が100人を超える事態）を参考にした。出現回数ではなく本人数で数える。99人ずつに分ける回避を累計で防ぐ。
- **訂正**：旧版は「個人情報保護法 第26条（100件超過）」と記載していたが誤り。同法の人数基準は1,000人超であり、100人超は番号法側の基準である。
- **トレードオフ**：累計はコレクターのメモリ上で行うため、再起動で消え、複数台では共有されない。本番では DB 集計かストリーム処理にする。警戒は「兆候」であり、法的判断は人が行う。

## ADR-10 依存ライブラリなしで実装する

- **背景**：学習目的として、フレームワークが隠している仕組みを自分で理解したい。
- **決定**：JDK 標準（HttpServer・HttpClient・仮想スレッド）と JDBC ドライバーだけで作る。サーブレット API は同じパッケージ名の最小サブセットを自作した（`servlet-api-lite`）。
- **理由**：本文の再読み込み・非同期送信・冪等性・認証などを自分で実装して理解できる。
- **トレードオフ**：本番品質のフレームワーク機能（コネクションプール、設定管理、セキュリティ）がない。Spring Boot の Starter 化（AutoConfiguration）は今後の課題とした。

## 第7章 自己レビューで見つけた欠陥と対応（v1 → v2）

v1 を自分でコードレビューし、実際に動かして再現できたものを修正した。

| No | 欠陥（v1） | 再現方法 | 対応（v2） |
|---|---|---|---|
| 1 | 64KB を超える本文が業務側で切れる | 200KB を送ると業務に64KB | 読んだ分を素通し・先頭だけコピー（ADR-02） |
| 2 | 同時挿入でハッシュチェーンが分岐 | 40件同時 INSERT で8か所 | 先頭行ロックで直列化（ADR-08） |
| 3 | UPDATE / DELETE ができ、警戒レベルがハッシュ対象外 | CRITICAL→INFO に書き換えても検出不可 | WORM トリガー、全項目をハッシュ、検証関数（ADR-08） |
| 4 | 収集 API の認証回避 | キーのヘッダーを付けないと 202 | 一致したときだけ通す・定数時間比較 |
| 5 | 監査コンソールの Stored XSS | URI に `<img onerror>` で実行 | textContent で表示、CSP、JSON 内の < > もエスケープ |
| 6 | 「SHA-256 Verified」表示が固定文字列 | HTML に直書き | 実際の検証結果を表示 |
| 7 | ユーザー不明時に特定の社員番号で記録 | ユーザーなしで送ると EMP_…0001 | ANONYMOUS。Who は認証結果のみ |
| 8 | X-Forwarded-For を無条件に信用 | ヘッダー偽装で接続元を詐称 | 信頼済みプロキシからのときだけ採用 |
| 9 | 再送処理が存在しない | 退避するだけで送り直さない | 再送スレッド・部分再送・冪等（ADR-05, 06） |
| 10 | DB 失敗でも 202 | — | 503（ADR-07） |
| 11 | 閾値の根拠条文の誤り・「以上」と「超」の混同 | 文書と `>= 100` | 番号法の基準に訂正、`> 100`、本人数で計数（ADR-09） |
| 12 | 「誤検知ゼロ」と記載 | ランダム12桁の約10%が通過 | 表現を訂正し、文脈判定を追加（ADR-04） |
