## 1. 背景と目的

### 1.1 背景
個人情報を扱う業務システムでは、「誰が・いつ・どこから・誰の情報を・何をしたか」を後から確認できる記録（アクセスログ）が求められる。
一方で、既存の業務システムを改修してログ出力を追加するのは、回帰テストの工数とリリースのリスクが大きい。

### 1.2 目的
1. 業務アプリのコードを変えずに、前段のフィルター1つで監査ログを取得する。
2. 監査ログに個人情報の生値を残さない（マスキングしてから外に出す）。
3. 特定個人情報（マイナンバー）の大量照会を検知し、担当者に知らせる。
4. 監査ログが後から書き換えられていないことを検証できるようにする。

### 1.3 スコープ

| 対象 | 対象外 |
|---|---|
| HTTP の業務 API に対するアクセスログ | DB 直接操作・バッチ処理のログ |
| マイナンバー・法人番号・電話番号・メール・基礎年金番号の検知 | 氏名・住所の検知（形式で判定できないため） |
| 1システム分のデモ（架空の顧客管理システム） | 複数システムの本番運用・冗長化 |

## 2. 関連法令と本システムの位置付け

| 法令等 | 該当する定め | 本システムでの扱い |
|---|---|---|
| 個人情報保護法 第23条 | 安全管理措置 | アクセスログの取得・改ざん検知で支援する |
| 個人情報保護法 第26条・施行規則第7条 | 漏えい等の報告。人数基準は **本人1,000人超**（ほかに要配慮個人情報・財産的被害・不正目的の類型） | 報告要否の判断はしない（人が判断する） |
| 番号法 第29条の4・委員会規則第2条 | 特定個人情報の漏えい等の報告。人数基準は **本人100人超** | この基準を参考に、社内監視の閾値を「1リクエスト（または10分累計）で本人数100人超」とした |
| 番号法施行令 第8条 | マイナンバーの検査用数字の計算方法 | 検知時のチェックディジット検証に使用 |
| JIS Q 15001（プライバシーマーク） | 個人情報保護マネジメントシステム | アクセスログの記録と点検を支援 |

> 本システムが付ける警戒レベルは「人が確認すべき兆候」であり、法的な判断ではない。
> 法令の条文・基準は改正されることがあるため、運用時は個人情報保護委員会の最新の情報を確認する。

## 3. アクター

| アクター | 説明 |
|---|---|
| 業務担当者 | 業務アプリで顧客情報を照会する社員（認証済み） |
| 監査担当者 | 監査コンソールでログと警戒を確認する |
| 監査センサー | 業務アプリに組み込むフィルター |
| 監査コレクター | ログを受け取り、判定・保存・検証する |
| DB 管理者 | DB を運用する。改ざんの脅威主体にもなりうる（内部不正） |

## 4. 機能要件

受入基準の右端は、確認するテスト（単体テスト＝UT、E2E 検証スクリプトの手順＝E2E-n）を示す。

| ID | 要件 | 受入基準 | 確認 |
|---|---|---|---|
| FR-01 | 業務アプリを改修せずに監査ログを取る | 業務処理クラスに監査のコードがない。フィルターを1つ足すだけで動く | 構成で確認 |
| FR-02 | 業務データを変えない（非侵襲） | 64KB を超える本文も業務側に全バイト届く | UT `CachingWrappersTest` / E2E-6 |
| FR-03 | 個人情報をマスキングしてから送る | 監査ログ・DB に生のマイナンバーが存在しない | UT `JapanAuditLoggingFilterTest` / E2E-1 |
| FR-04 | マイナンバーをチェックディジットで判定する | 番号法施行令の計算式どおり。文脈により確度 HIGH/MEDIUM を付ける | UT `MyNumberModulus11ValidatorTest` `JapanPiiDetectorTest` |
| FR-05 | 6何（Who/When/Where/Whom/What/How）を記録する | Who は認証結果のみ、Where は信頼済みプロキシ経由のときだけ X-Forwarded-For を採用 | UT / E2E-4, E2E-5 |
| FR-06 | 大量照会を検知する | 本人数 100人**超**で CRITICAL（100人ちょうどは対象外）。同一ユーザーの10分累計でも判定 | UT `AlertEvaluatorTest` / E2E-2, E2E-3 |
| FR-07 | 改ざんを検知できる | 行の変更・明細の変更・途中削除・末尾削除・全再計算を検出できる | DB 試験 / E2E-10, E2E-11 |
| FR-08 | 監査コンソールで確認できる | 認証必須。ログの値は HTML として解釈されない | UT `CollectorServerTest` / E2E-8 |

## 5. 非機能要件

| ID | 区分 | 要件 | 確認 |
|---|---|---|---|
| NFR-01 | 可用性 | コレクター停止中も業務は止めない（フェイルオープン）。停止中のログはローカルに退避し、復旧後に再送して欠損させない | E2E-9 |
| NFR-02 | 信頼性 | 再送で二重登録しない（traceId で冪等）。DB に書けないときは 503 を返し、センサーに再送させる | UT / DB 試験 |
| NFR-03 | 性能 | 業務スレッドは監査送信を待たない。監査用にコピーする本文は上限（既定64KB） | E2E 参考値 |
| NFR-04 | セキュリティ | 収集 API はセンサーキー必須（定数時間比較）。コンソールは Basic 認証＋CSP。秘密情報はコードに書かず環境変数で渡す | UT / E2E-7, E2E-8 |
| NFR-05 | データ最小化 | 本文は既定で送らない。DB にはマスキング値・件数などのメタデータだけを保存する | UT |
| NFR-06 | 保守性 | 依存ライブラリなし（JDK 標準＋JDBC ドライバーのみ）。単体テストと E2E スクリプトで再現可能 | — |

## 6. 前提・制約

- テストデータはすべて架空（氏名「架空 太郎n」、電話番号は実在しない局番 000、メールは example.com）。
- 監査用にコピーする本文には上限があるため、上限を超えた部分の個人情報は数えられない（6章の制約として記録し、運用で上限を調整する）。
- 分割照会の集計はコレクターのメモリ上で行うため、再起動で消え、複数台では共有されない。
