## 1. 導入手順

### 1.1 Docker Compose で起動（推奨）

```bash
cp .env.example .env          # POSTGRES_PASSWORD / SENSOR_KEY / CONSOLE_PASSWORD を変更
docker compose up -d --build
docker compose ps             # audit-db が healthy、他が running であること
```

### 1.2 既存の業務アプリへの組み込み（センサー）

業務アプリ側で行うのは、フィルターをチェーンの先頭に1つ足すことだけである。

```java
AuditSensorProperties props = AuditSensorProperties.fromEnv(System.getenv());
AuditSensorFactory.AuditSensor sensor = AuditSensorFactory.create(props);
// 例：フィルターチェーンの先頭に sensor.filter() を登録する
// 停止時は sensor.close()（キューに残ったログを退避してから終わる）
```

| 必須の環境変数 | 説明 |
|---|---|
| `SENSOR_KEY` | コレクターと同じキー |
| `COLLECTOR_URL` | 例 `http://audit-collector:8081/api/v1/collector/ingest` |
| `AUDIT_SYSTEM_CODE` | 業務システムの識別子 |
| `AUDIT_TRUSTED_PROXIES` | 前段にロードバランサー等がある場合、その IP（カンマ区切り）。空なら X-Forwarded-For は使わない |

### 1.3 DB の権限（本番想定）
アプリ用の DB ユーザーには `SELECT, INSERT` だけを与え、挿入トリガー関数は所有者権限（`SECURITY DEFINER`）で動かす。例は `scripts/schema.sql` の第8節。

### 2.2 E2E 検証（`scripts/e2e-verify.sh`）

業務アプリ → 監査フィルター → コレクター → DB を実際に通す。

| No | 確認内容 | 合格基準 |
|---|---|---|
| E2E-1 | 通常の照会 | ログが届き、マスキング値が記録され、生のマイナンバーがコレクターに存在しない |
| E2E-2 | 120人分の出力 | CRITICAL（1リクエストで本人数120人） |
| E2E-3 | 60人×2回 | 2回目で CRITICAL（10分累計） |
| E2E-4 | 未認証アクセス | 業務は401、ログは ANONYMOUS・401 |
| E2E-5 | ヘッダー偽装 | ユーザー・接続元とも偽装値が採用されない |
| E2E-6 | 200KB アップロード | 業務側の受信バイト数が 200000 |
| E2E-7 | 認証 | キー無し・誤キー → 401、コンソール API も認証必須 |
| E2E-8 | XSS | API が `<` で返す。コンソールに CSP |
| E2E-9 | コレクター停止 | 停止中も業務は200。退避され、復旧後に5件すべて到着（欠損0） |
| E2E-10 | チェーン検証 | OK（アンカーとも一致） |
| E2E-11 | 改ざん（任意） | DB 管理者がトリガーを外して書き換え → BROKEN |

## 3. 実施結果（2026-11-03）

### 3.1 実施環境
- Java 21 / PostgreSQL 16（TimescaleDB なし構成）/ Linux
- コレクター・業務アプリは Dockerfile と同じ javac コマンドでビルドし、ローカルプロセスとして起動
- コレクター停止は `COLLECTOR_STOP_CMD` / `COLLECTOR_START_CMD` にプロセス停止・起動のスクリプトを指定

### 3.2 結果

| 区分 | 結果 |
|---|---|
| 単体テスト | 47件 合格 / 0件 不合格 |
| E2E 検証（改ざん試験を含む） | 25項目 合格 / 0項目 不合格 |

障害試験（E2E-9）の記録：

| 時点 | sent | spoolBytes | resent | rejected | dropped |
|---|---|---|---|---|---|
| 停止中（5件リクエスト後） | 7 | 3,725 | 0 | 0 | 0 |
| 復旧後 | 7 | 0 | 5 | 0 | 0 |

停止中のリクエストの応答時間はいずれも 5ms 未満で、業務への影響はなかった。

### 3.3 追加試験：DB 管理者による全再計算（アンカーの効果）

トリガーを外して1行を書き換え、以降の全行のハッシュと先頭行を再計算した場合：

| 検証方法 | 結果 |
|---|---|
| DB 内の検証関数のみ | 問題0件（DB の中だけでは見抜けない） |
| DB の外のアンカーと照合 | `hash differs from anchor … (chain was rewritten)` で検出 |

### 3.4 追加試験：同時挿入

| 試験 | v1（旧） | v2（現行） |
|---|---|---|
| 異なるログ60件＋同一ログ20件を同時に INSERT | 40件同時で分岐8か所 | 61行・分岐0・検証問題0 |
| UPDATE / DELETE / TRUNCATE | 実行できた | すべて拒否 |

### 3.5 性能（参考値・同一マシンで各200回／100回）

| 操作 | 監査OFF（中央値） | 監査ON（中央値） |
|---|---|---|
| 顧客1件照会（約0.1KB） | 約1.1ms | 約0.9〜1.5ms（誤差の範囲） |
| 120件出力（約17KB・個人情報360項目） | 約1.9ms | 約4.8〜5.4ms（**約+3ms**） |

個人情報の検知・マスキングを業務スレッドで行っているため、個人情報を多く含む大きなレスポンスでは数ms増える。
監査用コピーは上限64KBなので増加には上限があるが、さらに減らすなら「検知を送信スレッド側へ移し、キュー満杯時だけ同期でマスキングして退避する」構成が考えられる（今後の課題）。
